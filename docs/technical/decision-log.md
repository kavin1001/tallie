## ADR-026 — Temporary phone-only manual-split preview

**Date:** September 26, 2026. **Authority:** explicit founder request to remove required passkeys for the demo. **Status:** locally implemented and tested; deployment evidence tracked separately. This narrowly qualifies ADR-021 for marked preview accounts.

**Decision:** require fresh browser-bound phone proof for demo signup/sign-in, mark these accounts persistently and use distinct `phone_demo` assurance. Enable it only with an explicit server flag in the beta preview launcher. Preserve identity/name on returning login. Keep existing passkey identities protected, all original proof/replay checks, and strong security/channel/receipt-command gates. Manual-split mutations require the enabled flag, matching account/session/phone and absence of passkeys. Kill-switch and credential-aware checks deny stale demo access. Use the existing 30-day rolling Better Auth session policy.

**Tradeoff and transition:** phone possession is weaker than a passkey and can expose demo history after number reassignment. This is a temporary, consenting-tester exception with payments disabled. On return to passkeys, existing demo sessions can reverify into restricted enrollment and preserve account identity; users without that session need a planned transition. Never relabel demo sessions as stronger assurance or downgrade existing passkey identities.

**Evidence:** 314 tests, including 35 identity and 27 social PostgreSQL cases; synthetic local browser flows cover new/returning signup, logout and stale completion. A separately approved empty-draft repair preserved proof/rate-limit evidence. See [identity integration](identity-integration.md) and [tracker](implementation-tracker.md).

### ADR-025 — Free hosted account preview before worker-backed beta

**Date:** September 26, 2026. **Status:** implemented and deployed; live HTTPS/session/access checks passed, native device journeys remain pending. **Authority:** founder explicitly authorized a private `kavin1001/tallie` repository and temporary Render hosting with a $0 infrastructure budget.

Use one free Render web service and one free PostgreSQL instance. Run additive, advisory-locked migrations before the web process starts and bounded identity-proof cleanup within the same instance. The launcher forces real-account beta mode and disables receipts, messaging intake/delivery and demo payments. Keep the full paid configuration separately for a future explicit upgrade.

This preserves useful account, passkey, recovery, contact, invitation and manual-split testing without idle worker charges. The tradeoffs are cold starts, limited memory, cleanup pausing during sleep, and a database that expires after 30 days without backups. The prototype must not promise continuous messaging or durable production history. Expired-proof authorization fails independently of maintenance deletion.

A temporary Render hostname is acceptable for founder testing. Use a fixed platform-provided HTTPS origin, and plan new passkey enrollment when moving to the eventual domain. Private S3 provisioning remains authorized only when AWS's account-specific Free plan and credit/expiry state establish no charges; it is unnecessary for this preview while receipt intake is disabled. Existing Sendblue phone-verification usage remains separate provider usage.

**Observed deployment:** [tallie-web.onrender.com](https://tallie-web.onrender.com) runs `d06a780`; free PostgreSQL has public access blocked and expires October 26, 2026. Blueprint sync and deployments are manual. AWS storage was deferred because the authenticated account's free-plan coverage was not established. Local tests, Linux CI, a constrained container smoke and public HTTPS checks passed; this does not establish native device or financial readiness.

**Revisit:** receipt/iMessage testing, database expiry, measured memory pressure, or the chosen permanent domain. [Render free-plan limits](https://render.com/docs/free), [deployment guide](deployment.md).

## Accepted technical costs

- Reconciliation can leave an uncertain payment pending longer than the user wants. Evidence is needed before another attempt is safe.
- The implemented primary invitation path requires account enrollment and a passkey before private expense access. Phone-only guest access is deferred by ADR-022; the earlier guest→app design would repeat verification rather than promote a guest session without evidence.
- Unfamiliar-device login to an existing financial account can require recovery even after SMS verification. Phone possession alone does not safely identify the prior account owner.
- Chat authority expires and requires renewal from a trusted app session; this applies to historical status reads as well as request publication. Phone routing alone cannot provide permanent identity assurance.
- A Venmo handoff may need another tap after provider cancellation because mobile browsers restrict deferred app launches. Never bypass the payment-path reservation to save that tap.
- No app can revoke a Venmo URL already exported by the user. Manual external settlement and duplicate-resolution UX remain necessary.
- The initial ADR-001 design combined future payment and message credentials in the core worker. ADR-023 supersedes that cost with a fourth messaging process/service. Local processes and the prepared Blueprint still share a database owner role; separate SQL grants remain a real hardening gap.

## Implementation addendum — September 25, 2026

- **Name:** Tallie replaces the temporary Even working name.
- **Workspace tooling:** npm workspaces selected. The installed pnpm shim failed to resolve its runtime; npm is available and provides a checked-in lockfile without a global tool repair.
- **Runtime:** Node 24, Next.js 16.3.6, React 19.3, Kysely 0.29.6 and PostgreSQL 17. Kysely was upgraded during the initial dependency audit to eliminate known advisories. Exact resolved dependencies live in the lockfile.
- **First identity/payment adapter:** isolated, synthetic demo identity and durable local simulation allow end-to-end UX and database verification while founder obtains provider accounts. This does not replace the production auth/recovery or provider integration design. Every live capability is false and demo mode is explicit.
- **Rounding:** algorithm `usd-largest-remainder-v1` rounds each item and each receipt adjustment separately, with stable immutable-ID ties. Tax/tip default proportionally to net items; explicit equal overrides exist in domain code. A fully discounted receipt with a positive proportional adjustment fails and requires an explicit rule. Frontend currently offers the proportional default only.
- **API versioning:** internal same-origin `/api` routes implement the first slice. External versioned `/v1` contracts remain planned.
- **Simulator transaction:** local operation completion, settlement, request state and activity can commit atomically because no external service is called. Real provider submission will require durable dispatch/inbox/outbox and uncertain-outcome reconciliation; it cannot inherit this atomicity claim.

## ADR-019 — Sendblue phone verification spike, September 26, 2026

**Historical selection evidence below.** ADR-021 records the later implemented identity bridge; it does not retroactively turn the original public-doc spike into device verification.

**Owner:** identity/channel implementation. **Affected:** signup, guest receipt access, phone ownership and channel connection; financial approval invariants remain unchanged.

The founder proposed Sendblue for verification as well as messaging. Official Verify documentation uses the same API credentials for both. It documents a user-initiated code message, provider-confirmed approval, service IDs and separately signed Verify callbacks. This fits the proposed Messages entry point and removes Twilio as a prerequisite for the next integration experiment. This is a plan change, not a deployed adapter or claim of account availability.

Bind the verification to a server-created signup transaction or signed-in account, expected phone, session nonce, purpose, service and expiry. Consume approved proof once and rotate/create only the appropriate scoped session. Do not accept an arbitrary browser-supplied verification SID, a composer-open event or an unverified webhook. Existing-account recovery, phone reassignment, messaging consent, Natural activation and debit approval keep their independent checks.

Validate iPhone and independently establish Android/SMS support before making this the sole onboarding route. Account-assigned verification lines may fall back to a shared pool, so the verification thread may differ from the continuing agent thread. Better Auth reverse-OTP integration must use a supported adapter/plugin mechanism and pass replay/concurrency tests. The existing demo stays available while these gates are open; Twilio remains a possible fallback.

Sources: [Sendblue Verify](https://docs.sendblue.com/api-v2/verify/), [API credentials](https://docs.sendblue.com/getting-started/credentials/). Evidence: public docs only, no credentials or device flow tested.

## ADR-020 — Bounded live receipt interpretation and development-only phone proof

**Date:** September 26, 2026. **Status:** Implemented locally, verified as described in tracker. **Authority:** founder supplied credentials and authorized implementation; financial launch gates remain open.

1. Use the configured OpenAI key only in the receipt worker. Pin `gpt-4.1-mini-2025-04-14` as the first measured candidate; three synthetic live fixtures passed, but a diverse benchmark must inform the eventual model choice. Strict schema/no tools/explicit review and deterministic validation are required regardless of model.
2. Keep receipt photos owner/session-private until pixel redaction and participant delivery pass their gates. Publish reviewed structured expense values only. This enables useful capture without falsely claiming the agreed full-redacted-receipt feature is complete. Absence remains unknown; the reviewer explicitly confirms zero where appropriate.
3. Use Sendblue Verify service access for a `connect_test` adapter before connecting it to production auth. Require exact returned phone/service/challenge evidence and fail closed on missing terminal phone evidence. Real device testing and signed callbacks precede a production identity bridge. No demo proof grants login or financial authority.
4. Use private local files and application-owned PostgreSQL jobs in the localhost slice. The tradeoff is easy iteration with limited deployment portability and shared local OS/DB trust. Public staging requires persistent private storage, restricted roles, resource isolation, real account assurance and abuse controls. Dynamic private file accesses opt out of bundler tracing; ignore rules and generated-asset scans verify the boundary.
5. Preserve optional-provider development: disabling receipt reading leaves manual splits usable. Provider spend is bounded by upload/attempt/token ceilings, not represented as an exact currency budget.

**Revisit:** after the founder's phone test, fifty-image consented/synthetic evaluation, Natural program acceptance, and shared-staging design. [Receipt guide](../../packages/receipts/README.md), [Sendblue guide](sendblue-integration.md), [tracker](implementation-tracker.md).

## ADR-021 — Persistent identities require a passkey before private access

**Date:** September 26, 2026. **Owner:** identity implementation. **Status:** implemented with local PostgreSQL and synthetic cryptographic verification; supported-device/final-domain evidence pending. **Affected:** signup, private history/receipt access, recovery, channel enrollment and revocation. Extends ADR-019 and supersedes the initial optional-after-first-action passkey timing.

**Decision:** use the pinned Better Auth session/passkey surfaces with a purpose-bound reverse-OTP bridge. A new phone proof creates an immutable app identity and restricted enrollment session. A user-verified passkey establishes private app access. Existing accounts cannot sign in with number possession alone; recovery requires a fresh correctly bound phone proof plus a saved one-use recovery code. Keep identity encryption independent of the demo phone key. Restrict security endpoints to recent assurance and prevent removal of the last passkey.

**Alternatives and cost:** phone-only login is smoother but exposes history to reassigned numbers; optional delayed enrollment leaves that same ambiguity for accounts with private drafts. Required enrollment adds a device step and excludes unsupported authenticators until an equally strong alternative exists. Support recovery and number-change procedures remain unfinished; do not improvise a phone-only override.

**Evidence and rollout:** migration005 and migration009 create persistent identity/session-bound channel proof independently of all demo tables. Local tests exercise actual signed cookies, valid P-256 registration/assertions, missing user verification, replay, concurrent recovery and revocation. The founder's earlier successful development phone proof is separate evidence. Preserve a stable HTTPS relying-party domain before enrollment; localhost passkeys do not migrate automatically. [Identity integration and tests](identity-integration.md).

**Revisit:** actual device coverage or observed enrollment abandonment justifies testing a strong alternate factor; never weaken existing-account ownership based only on transport convenience.

## ADR-022 — Private invitations and shared expenses use real identities

**Date:** September 26, 2026. **Owner:** social implementation. **Status:** implemented with real PostgreSQL concurrency/privacy tests; hosted two-account observation pending. **Affected:** friend resolution, invitation context through signup, participant access and obligation creation. Defers the guest implementation from ADR-011 and supersedes the proposed anonymous amount preview.

**Decision:** maintain contacts, invitation claims and expense allocations in real-account tables separate from demo and financial execution. Contacts use immutable UUIDs, encrypted intended phones, keyed fingerprints and private owner labels. Do not reveal account existence on contact creation. Resolve names only when exact and unique. Fragment links carry random tokens; anonymous inspection is generic. Store a lookup digest plus encrypted token for idempotent response recovery. A claim requires the exact intended verified number and established account assurance, with account-pair/invitation/share locks. A friendship does not reveal earlier unclaimed obligations; an expense link grants only its matching share.

**Alternatives and cost:** an anonymous expense preview reduces signup uncertainty but leaks financial context to forwarded links and preview infrastructure. A phone-only guest route adds a second identity/capability lifecycle and can downgrade enrolled-account security. This release uses the user's primary signup path, preserves link context, and postpones guest access. Passkey enrollment adds friction; the UI must explain and retain the request. Retaining encrypted tokens supports safe retries but requires protecting and eventually rotating encryption keys.

**Evidence and rollout:** migration006 introduces the isolated social tables. Tests cover opposite-direction invitations, concurrent claims/revocation, ambiguous names, strong-session checks, exact allocation, privacy, permanent publication identity and balance totals beyond the displayed history window. Owner cancellation keeps the original allocation and is not settlement. No social mutation sends a provider message, creates financial consent or runs the payment simulator. [Social integration](social-integration.md).

**Revisit:** a validated, bounded guest bridge or new product requirements justify a separate design. Full redacted receipt images, corrections/disputes, blocking and payments remain explicit follow-up work.

## ADR-023 — Four roles share durable application commands

**Date:** September 26, 2026. **Owner:** application/messaging integration. **Status:** implemented and locally verified; ordinary provider/device behavior pending. **Affected:** process isolation, job durability, web/chat consistency, consent and unknown delivery. Supersedes ADR-001's three-role deployment and ADR-004's immediate Graphile installation.

**Decision:** run web, core maintenance, receipt and messaging as separate processes/services. `packages/app-services` wires account authorization, contact resolution, receipt ingestion and social publication for both web and message workers. Application-owned PostgreSQL inbox/outbox/draft/job tables supply transactional reservations, leases, deduplication and recovery. A message draft publishes under one permanent domain identity across chat and web completion, independent of mutable draft versions. Equal splits require an expiring exact review; item/custom choices continue in the web composer. No model or inbound payment word can authorize a debit.

**Messaging controls:** authenticate ordinary callbacks with the documented static secret header, fetch canonical provider evidence before commands, enforce short-lived grants tied to the originating strong session, and serialize STOP/revocation/publication. Unknown send outcomes are retained, never automatically repeated. Media fetches use fixed trusted hosts, bounded streams and public-address pinning. Keep provider fields, phones, transcripts and receipt URLs out of ordinary logs. Sending defaults to disabled. [Messages integration](messaging-integration.md).

**Alternatives and cost:** Graphile can reduce generic queue maintenance; a broker adds another durability boundary. Current application tables keep specialized grant/receipt/publication transactions inspectable, but we own lease fencing, fairness, retention, retries and stuck-work recovery. Four containers cost more than one worker. Role-filtered provider secrets reduce exposure, while shared local OS/DB access and the Blueprint's common DB credential remain unfinished isolation work.

**Evidence and rollout:** database tests use concurrent clients and injected provider transports; cross-package tests assert that chat/web publication creates one social expense and zero financial operations. Later migrations add a receipt hydration cursor and immutable web-publication reservation. Hosted callbacks, provider-verified shared-line contacts, actual media and ambiguous live sends still need consented device verification. [Runtime/deployment roles](deployment.md).

**Revisit:** measured queue volume, operational complexity or new multi-provider workflows justify Graphile, a broker or a workflow engine. Preserve domain idempotency and uncertain-outcome rules through any migration.

## ADR-024 — Prepare container hosting with private S3 before provisioning

**Date:** September 26, 2026. **Owner:** deployment preparation. **Status:** artifacts prepared and locally checked; no hosting, DNS, bucket or provider configuration created. **Affected:** deployment reproducibility, private receipt retention, runtime credentials and stable passkey origin. Implements the preparation portion of ADR-015/017 without claiming their hosted gates are closed.

**Decision:** one multi-stage digest-pinned Node 24 Dockerfile serves all four commands. The Render Blueprint builds that Dockerfile per service, runs migrations once through the web pre-deploy hook, disables preview/automatic deployment and external database access, and keeps outgoing messaging disabled. Use S3 for cross-service receipt storage; no Render disk is treated as a shared filesystem. Separate IAM principals grant web source writes/normalized reads, receipt source reads/normalized writes/deletes, and message source writes. Fixed keys, private access, encryption, owner checks and lifecycle cleanup accompany application expiry.

**Alternatives and cost:** a single shared disk cannot support independent Render services; public image URLs violate receipt privacy. S3 adds an account, scoped credentials and operational checks. Retaining `tsx`/locked build tooling in the image increases size until worker bundles are compiled separately. The current Blueprint's shared database owner credential is an explicit gap, not the selected long-term permission model. A two-day lifecycle makes orphans eligible for asynchronous deletion; it is not a hard 48-hour deletion promise.

**Evidence and rollout:** official Render schema validation passed. A native Linux ARM64 container production build and isolated-schema web/three-worker smoke passed with fake provider configuration; demo routes were unavailable in beta and anonymous social access was denied. The AMD64 emulation run compiled then failed under QEMU during page collection, so native AMD64 remains unverified. S3 request/permission contracts have mocked SDK evidence, not live AWS evidence. Before provisioning, supply a stable HTTPS origin, hosting/Git access, private bucket and restricted runtime secrets; review the concrete resource plan. [Deployment guide](deployment.md), [storage policies](deployment-storage.md).

**Revisit:** native host, live bucket/IAM, proxy/cookie, final-domain passkey, webhook, monitoring or restore tests expose a gap. Natural approval and payment integration stay independent of a successful deployment.
