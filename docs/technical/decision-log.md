## Decisions

## ADR-032 — Masked bank discovery, explicit ACH consent and isolated activation testing

**Date:** September 26, 2026. **Authority:** founder authorizes implementation and reasonable assumptions; the existing Natural local-test/release gate remains. **Status:** bank-read adapter implemented locally with injected-provider tests; bank money movement and HTTPS/device integration remain separate evidence gates.

**Decision:** use a separate production-agent GET adapter to discover the authenticated customer's linked banks. Resolve customer identity from the accepted account connection, verify the platform and exact customer ownership, retain explicit bounded pagination and reread any selected bank by ID. Return only masked institution/account-display metadata, classified connection readiness and withdrawal methods. No bank credentials, account names, account/routing numbers or arbitrary provider metadata enter the DTO. The adapter cannot link, delete, deposit, withdraw or pay.

**Bank-flow defaults selected:** customer-owned linking on Natural's dashboard; standard ACH for the first release; per-action source/destination, amount, fee and timing review followed by fresh explicit consent. No automatic topping up and no alternative bank selection after failure. Unknown dispatch outcomes retain the original operation identity for reconciliation. Documented bank-funded request fulfillment can avoid a separate funding step, but production dispatch, exact grant behavior and the live lifecycle must be verified before it becomes a product promise.

**Evidence boundary:** `wallets.read` explicitly authorizes customer bank reads in the public contract, so discovery adds no new grants. The provider resource has no separate verified flag; active resource plus active connection is display readiness only. `availableMethods` concerns withdrawals and does not prove debit eligibility or program-level instant access. The permission enum includes `wallets.deposit` and `wallets.withdraw`, but exact mutation grant combinations and account-specific fees/limits remain unresolved. No speculative `payment_requests.*` permission is introduced. 37 new injected-response tests cover these adapter boundaries; no live bank or runtime behavior is established by that suite.

**Isolation selected:** use a separate HTTPS test origin, dedicated test process/database and dedicated configuration/credentials for production hosted activation. Do not tunnel the ordinary sandbox development server or reuse its account/session records. Keep financial dispatch and phone-demo authority disabled. Temporary hostnames trade quick setup for passkey portability: credentials are scoped to the relying-party domain, so a hostname change requires fresh test enrollment or an explicitly supported recovery path. No final-domain migration is implied. Runtime setup/validation is recorded independently in the operations guide and tracker.

**Tradeoffs:** a hosted bank step adds friction but avoids collecting sensitive credentials before Natural provides a supported embedded contract. Small explicit pages bound latency and provider cost but require the future UI to preserve pagination. A masked DTO reduces accidental disclosure while provider IDs remain server-bound selection data. Standard ACH and explicit consent limit the initial surface; they do not resolve settlement timing, returns, fees or KYC through assumptions. Revisit embedded linking, instant withdrawals and grants only with documented contracts and account-specific test evidence.

## ADR-030 — Durable canonical reconciliation and bounded event retention

**Date:** September 26, 2026. **Status:** implemented locally; provider-read and implementation evidence recorded in the tracker. Founder local-test/release gate remains active.

**Decision:** enqueue sandbox send/funding reconciliation in the journal transaction via migration017, including backfill. Workers claim bounded jobs with expiring leases and generation fencing, perform provider I/O outside database locks, then lock journal before job when saving. A shared monotonic observation function updates browser and worker paths consistently. Unknown sends retain their permanent operation identity and are searched in bounded pages; unknown deposits without a provider ID require investigation. A scan finding nothing does not authorize replacement.

**Events and controls:** migration018 stores environment/platform/event identities and signed-payload hashes. Verify exact-byte Standard Webhooks signatures, cap reads/time, reject mismatches, commit before acknowledging, encrypt bodies for 30-day retention and retain dedupe identity thereafter. Authenticated financial events only wake canonical reads. Migration019 adds submission pause/history and worker heartbeats. Pause serializes with new submission reservation; an already admitted call can complete. Reconciliation continues while paused. Production resume is unavailable in this release.

**Tradeoffs:** PostgreSQL keeps dispatch history and work scheduling under one durability boundary, but Tallie owns lease/retry/fencing code and recovery tools. Poll completed sandbox operations for 60 days with reduced frequency, then rely on verified wakeups; this bounds routine cost and is not financial finality. Exposing only read methods to workers reduces accidental mutation, but the underlying provider key can retain greater permissions and shared DB credentials still need restriction. Health CLI output is implemented; external alert delivery is not configured.

**Supersedes:** ADR-028/029's browser-trigger-only reconciliation limitation. Does not generalize sandbox journals into a production debit ledger. See [operations runbook](payment-operations.md).

## ADR-031 — Hosted production connection is separate from payment execution

**Date:** September 26, 2026. **Authority:** founder confirms Natural approved P2P; production setup is still needed. **Status:** implemented locally with injected-provider/PostgreSQL evidence; no live production connection observed.

**Decision:** independent production keys/IDs, fixed production transports and a strict non-preview beta flag. Require a verified account phone, enrolled passkey and recent strong assurance before journaling one invitation attempt. Natural hosts identity/account setup. Store an encrypted continuation URL and account-bound hashed return token; a return only restores navigation. Do not repeat an ambiguous invitation because production invitation creation has no documented idempotency guarantee.

Only the production accepted-invitation event enters an activation worker. Re-fetch its canonical event and exact invitation/agent/platform/customer relation, verify current grants and bounded permissions, then verify the selected active standard USD agent-default wallet. Recheck the saved phone binding before committing. Production financial events remain quarantined, production debits cannot resume, and all response DTOs report money movement disabled. A connected record is historical setup evidence; future debits must refresh grants/eligibility.

**Tradeoffs and unresolved evidence:** hosted setup avoids collecting KYC fields in Tallie but adds an app switch and provider dependency. Targeted phone invitations still need an observed forwarded-link identity test. The provider agent key's exact association requires issuance evidence; platform identity alone is insufficient. Expired/unknown/already-connected invitations need audited recovery before rollout. Bank funding/cash-out and real debits are separate implementation work. Default-off code permits review now without claiming any of those live paths work.

## ADR-029 — Explicit sandbox splits use one reserved payment attempt per share

**Date:** September 26, 2026. **Authority:** founder requested the P2P build and approved a $100/month ceiling. **Status:** implemented locally; implementation and provider evidence tracked separately below. Natural changes remain local until the founder tests and approves release.

**Decision:** new web-created expenses can explicitly opt into `payment_environment=sandbox`. Existing expenses and normal new expenses default to `manual`; chat publication cannot opt in. Test payments never reduce manual balances. Each non-owner test share is capped at $100 and can be paid only by the claimed, current phone-bound debtor to the expense owner's separately connected read-only Natural sandbox customer. The browser supplies a share UUID, never the amount, destination or provider IDs. A ten-minute exact review fixes sender/source, debtor, creditor, amount, note, share and previous attempt sequence. Confirmation rechecks the tuple and saves one durable provider operation before I/O.

**Concurrency and recovery:** lock expense, then share, then review. An additive partial unique index reserves the share across separate review IDs/keys; duplicate confirmations return their existing operation. Only canonical `FAILED` or `RETURNED` with a provider payment ID permit a newly reviewed replacement or owner cancellation. Unknown, incomplete, noncanonical failure and completed sends retain exclusivity. A changed attempt sequence invalidates earlier unconfirmed reviews. Canonical return remains monotonic. Sequential attempt IDs, rather than timestamps, determine the displayed current attempt. Both participants read the same saved status; only the debtor gets their spendable wallet/funding details.

**Experience:** an explicit test checkbox in the composer, inline receiving/sending activation, exact-share review, one-time appropriately sized test deposit and distinct test totals preserve the request context. Network uncertainty retains the exact approval and exposes a same-approval recovery action. A canonical failed/returned payment requires fresh explicit consent. Payments remain sandbox direct-wallet sends; this does not claim bank-funded fulfillment or a production obligation ledger. Reconciliation is read-triggered until a durable webhook/worker milestone.

**Tradeoffs:** reusing the existing narrow send journal makes the P2P slice testable without inventing a second dispatch implementation. It does not fulfill the planned production append-only settlement ledger, disclosures, fees, bank funding, withdrawals or late-event processing. Separate synthetic sender and receiver customers are still a lab-specific extra step. Definitive failures without canonical provider identity remain conservatively reserved for investigation. Only one test deposit is supported per sender; an exhausted wallet needs a smaller test split, not a database balance reset.

**Budget:** the new $100/month ceiling supersedes ADR-025's earlier $0 constraint. No resource was upgraded in this slice. The [launch plan](launch-plan.md) records a $66.50/month fixed Render proposal plus variable costs, with paid Sendblue pricing called out separately. Release approval remains independent of the budget authorization.

**Evidence:** migration016; shared-expense projections and cancellation guards; account-authenticated share state/review/confirm routes; local PostgreSQL race/return tests. The full check passed 497 tests across30 files, formatting, TypeScript and build at the initial slice. Browser checks observed explicit test creation, separate balances and cancellation; temporary QA records were removed. Current provider observations and any later targeted checks are in the [tracker](implementation-tracker.md).

**Revisit:** production program activation, observed failure/return semantics, supported funding/withdrawal, durable reconciliation, stronger debit authentication or multiple funding sources. Do not generalize the phone-demo sandbox exception to real money.

## ADR-028 — Separate synthetic send grant and exact direct-send review

**Date:** September 26, 2026. **Owner:** Natural sandbox implementation. **Affected:** local test-dollar onboarding, deposit, direct send and status recovery; no production obligation or collection lane. **Status:** implemented locally; one authenticated local Natural sandbox deposit/direct-send journey verified; founder release approval pending.

**Context:** the first Natural test customer has only read permissions. Expanding that grant in place would blur what the founder already accepted and could create payment authority for a connection designed to display balances. We need a way to exercise a real provider payment command in sandbox without implying that Tallie splits are collectible or that consumer P2P is approved.

**Decision:** create a second synthetic PERSON, bound to the same authenticated Tallie account but stored in a separate connection table, with the fixed `party.read`, `wallets.read`, `wallets.balance`, `payments.read` and `payments.create` delegation. Keep the first customer read-only. The sender can make one explicit test deposit and send at most $100 per reviewed direct payment to their separate read-only test account or an exact connected contact with a read-only test account. A short-lived server-built review binds sender, source wallet, recipient, amount and note; a second explicit confirmation is required before dispatch. Persist one immutable operation and idempotency key before the provider call. Concurrent or repeated confirmation of that review uses the same saved operation. A send with uncertain outcome is reconciled by canonical payment ID or operation tag and is never resubmitted; a deposit with uncertain outcome may be explicitly retried with its original key inside 24 hours. Current provider wallet reads supply displayed balances. A later `RETURNED` must not regress to `COMPLETED` on a stale read.

**Alternatives and cost:** upgrading the first grant would avoid a second customer but weaken its read-only boundary; sending directly from a browser-supplied party or wallet would make identity and source binding unverifiable. The second synthetic customer adds setup steps, duplicate test identities and wallet state. Reconciliation is currently triggered by local state reads, so a sleeping web role cannot discover late changes. The journal is deliberately separate from `social_shares`: it neither settles an expense nor supplies a production ledger or webhook inbox.

**Authentication and release:** a marked phone-demo account can perform these **test-dollar-only** actions under the local beta/preview/phone triple gate and current session/phone binding, with explicit review and confirmation. This exception cannot become production payment authority; real money still requires the strong identity, consent, obligation and reconciliation design in ADR-006–009/021. Natural transport remains pinned to the sandbox origin and role-specific sandbox keys. Founder testing and approval are required before any push or deployment. The hosted phone-demo release remains separate.

**Provider-scope follow-up:** the platform/provisioning key could provision and fund a synthetic customer but received HTTP 403 on that customer's wallet GET. Funding now checks the exact active standard wallet under the customer-scoped agent credential; the platform key performs its own-party/customer checks and sandbox deposit. Mixing these scopes caused a valid test funding path to fail. Background send-state and fund HTTP calls also no longer transition a ready sending connection into `verifying`; state reads current delegation and balance directly, while explicit setup retains refresh semantics. This avoids a polling/funding race with review or confirmation at the cost of separate read and setup-state paths.

**Funding recovery follow-up:** a `FAILED` deposit without a canonical provider transfer ID may be explicitly retried with the same immutable amount/source/operation/key within 24 hours. A canonical failed transfer ID is terminal. An expired submission lease is presented as unknown and retryable within the window. A later rejected preflight cannot turn an earlier unknown attempt into known failure. Direct sends remain read-reconciled and are not resubmitted. These rules preserve the distinction between an attempted command and a proved provider outcome.

**Evidence:** migrations014/015 and the send connection/journal services are locally implemented. The full `npm run check` passed formatting, TypeScript, **458 tests across 29 files**, and build; automated provider tests are injected/local evidence. An authenticated local Natural sandbox browser journey then showed sender setup ready, a completed $25 test deposit, one completed $1 direct send to that Tallie account's distinct read-only receiving customer, sender balance $24 and receiver available/total $1. Reload retained both balances, the confirmed deposit and exactly one completed $1 history entry. This is sandbox evidence for that path only; `natural:check` separately establishes live read-only credential/platform/agent observations. No push or deployment occurred. See [Natural runbook](natural-integration.md) and [implementation tracker](implementation-tracker.md).

**Revisit:** before any production P2P design or release. Verify program approval, two-person recipient eligibility, funding, fees, return timing and an always-on signed-event/reconciliation path before connecting a social obligation. The observed self-account sandbox transfer does not establish those capabilities.

## ADR-027 — Durable synthetic sandbox setup before real payment activation

**Date:** September 26, 2026. **Authority:** founder obtained a Natural key and requested implementation. **Status:** implemented locally; original read-only synthetic customer and wallet observed in the authenticated local sandbox. **Scope:** sandbox account creation, balances and provider client.

**Decision:** create one synthetic PERSON per explicitly consenting Tallie account through Natural's simulation invite/accept endpoints. Persist the expected platform/agent/read permissions and stable keys before external calls. Use short leases with generation fencing; calls never hold SQL locks. Treat transport/409/malformed mutation outcomes as unknown, retain operation identities, and stop mutation retries after 24 hours. Current delegation and exact owned wallets are checked before storing refreshed balances. Browser sees local UUIDs and clearly labeled test amounts only; null is unavailable.

**Authentication:** ordinary account session checks apply. The temporary marked phone-demo identity can create/read only synthetic sandbox accounts under its existing triple gate. This exception grants no real-payment authority. Provider keys must be sandbox-specific and the base is fixed; one literal opt-in controls the UI and web credential forwarding. Default remains disabled.

**Tradeoffs:** production phone/email invitations do not share the sandbox simulation contract, and production invitation creation has no documented idempotency guarantee. Do not generalize this service into production enrollment. The free web role holds separate provisioning and agent clients, avoiding a new paid worker; process/DB privilege isolation remains a production milestone. Credentials alone do not establish P2P approval or agent-key association. This original connection remains read-only; ADR-028 adds separate sandbox-only routes and a separate grant for test sends.

**Next:** ADR-028's authenticated local self-account deposit/direct-send path has now passed. It does not implement real-account obligation lanes, signed webhook inbox or production reconciliation. Verify two-person eligibility, fees, funding and return behavior independently before request settlement.

## ADR-026 — Temporary phone-only manual-split preview

**Date:** September 26, 2026. **Authority:** explicit founder request to remove required passkeys for the demo. **Status:** locally implemented and tested; deployment evidence tracked separately. This narrowly qualifies ADR-021 for marked preview accounts.

**Decision:** require fresh browser-bound phone proof for demo signup/sign-in, mark these accounts persistently and use distinct `phone_demo` assurance. Enable it only with an explicit server flag in the beta preview launcher. Preserve identity/name on returning login. Keep existing passkey identities protected, all original proof/replay checks, and strong security/channel/receipt-command gates. Manual-split mutations require the enabled flag, matching account/session/phone and absence of passkeys. Kill-switch and credential-aware checks deny stale demo access. Use the existing 30-day rolling Better Auth session policy.

**Tradeoff and transition:** phone possession is weaker than a passkey and can expose demo history after number reassignment. This was selected with payments disabled in the hosted preview; ADR-028 later permits local synthetic test-dollar actions only, with their own explicit review. On return to passkeys, existing demo sessions can reverify into restricted enrollment and preserve account identity; users without that session need a planned transition. Never relabel demo sessions as stronger assurance or downgrade existing passkey identities.

**Evidence:** 314 tests, including 35 identity and 27 social PostgreSQL cases; synthetic local browser flows cover new/returning signup, logout and stale completion. A separately approved empty-draft repair preserved proof/rate-limit evidence. See [identity integration](identity-integration.md) and [tracker](implementation-tracker.md).

### ADR-025 — Free hosted account preview before worker-backed beta

**Date:** September 26, 2026. **Status:** implemented and deployed; live HTTPS/session/access checks passed, native device journeys remain pending. **Authority:** founder explicitly authorized a private `kavin1001/tallie` repository and temporary Render hosting with a $0 infrastructure budget.

Use one free Render web service and one free PostgreSQL instance. Run additive, advisory-locked migrations before the web process starts and bounded identity-proof cleanup within the same instance. The launcher forces real-account beta mode and disables receipts, messaging intake/delivery and demo payments. Keep the full paid configuration separately for a future explicit upgrade.

This preserves useful account, passkey, recovery, contact, invitation and manual-split testing without idle worker charges. The tradeoffs are cold starts, limited memory, cleanup pausing during sleep, and a database that expires after 30 days without backups. The prototype must not promise continuous messaging or durable production history. Expired-proof authorization fails independently of maintenance deletion.

A temporary Render hostname is acceptable for founder testing. Use a fixed platform-provided HTTPS origin, and plan new passkey enrollment when moving to the eventual domain. Private S3 provisioning remains authorized only when AWS's account-specific Free plan and credit/expiry state establish no charges; it is unnecessary for this preview while receipt intake is disabled. Existing Sendblue phone-verification usage remains separate provider usage.

**Observed deployment:** [tallie-web.onrender.com](https://tallie-web.onrender.com) runs `d06a780`; free PostgreSQL has public access blocked and expires October 26, 2026. Blueprint sync and deployments are manual. AWS storage was deferred because the authenticated account's free-plan coverage was not established. Local tests, Linux CI, a constrained container smoke and public HTTPS checks passed; this does not establish native device or financial readiness.

**Revisit:** receipt/iMessage testing, database expiry, measured memory pressure, or the chosen permanent domain. [Render free-plan limits](https://render.com/docs/free), [deployment guide](deployment.md).

## Accepted technical costs

- Reconciliation can leave an uncertain payment pending longer than the user wants. Evidence is needed before another attempt is safe.
- The implemented primary invitation path requires account enrollment and a passkey before private expense access. Phone-only guest access is deferred by ADR-022; the earlier guest→app design would repeat verification rather than promote a guest session without evidence.
- Unfamiliar-device login to an existing financial account can require recovery even after SMS verification. Phone possession alone does not safely identify the prior account owner.
- Chat authority expires and requires renewal from a trusted app session; this applies to historical status reads as well as request publication. Phone routing alone cannot provide permanent identity assurance.
- A Venmo handoff may need another tap after provider cancellation because mobile browsers restrict deferred app launches. Never bypass the payment-path reservation to save that tap.
- No app can revoke a Venmo URL already exported by the user. Manual external settlement and duplicate-resolution UX remain necessary.
- The initial ADR-001 design combined future payment and message credentials in the core worker. ADR-023 supersedes that cost with a fourth messaging process/service. Local processes and the prepared Blueprint still share a database owner role; separate SQL grants remain a real hardening gap.

## Implementation addendum — September 25, 2026

- **Name:** Tallie replaces the temporary Even working name.
- **Workspace tooling:** npm workspaces selected. The installed pnpm shim failed to resolve its runtime; npm is available and provides a checked-in lockfile without a global tool repair.
- **Runtime:** Node 24, Next.js 16.3.6, React 19.3, Kysely 0.29.6 and PostgreSQL 17. Kysely was upgraded during the initial dependency audit to eliminate known advisories. Exact resolved dependencies live in the lockfile.
- **First identity/payment adapter:** isolated, synthetic demo identity and durable local simulation allow end-to-end UX and database verification while founder obtains provider accounts. This does not replace the production auth/recovery or provider integration design. Every live capability is false and demo mode is explicit.
- **Rounding:** algorithm `usd-largest-remainder-v1` rounds each item and each receipt adjustment separately, with stable immutable-ID ties. Tax/tip default proportionally to net items; explicit equal overrides exist in domain code. A fully discounted receipt with a positive proportional adjustment fails and requires an explicit rule. Frontend currently offers the proportional default only.
- **API versioning:** internal same-origin `/api` routes implement the first slice. External versioned `/v1` contracts remain planned.
- **Simulator transaction:** local operation completion, settlement, request state and activity can commit atomically because no external service is called. Real provider submission will require durable dispatch/inbox/outbox and uncertain-outcome reconciliation; it cannot inherit this atomicity claim.

## ADR-019 — Sendblue phone verification spike, September 26, 2026

**Historical selection evidence below.** ADR-021 records the later implemented identity bridge; it does not retroactively turn the original public-doc spike into device verification.

**Owner:** identity/channel implementation. **Affected:** signup, guest receipt access, phone ownership and channel connection; financial approval invariants remain unchanged.

The founder proposed Sendblue for verification as well as messaging. Official Verify documentation uses the same API credentials for both. It documents a user-initiated code message, provider-confirmed approval, service IDs and separately signed Verify callbacks. This fits the proposed Messages entry point and removes Twilio as a prerequisite for the next integration experiment. This is a plan change, not a deployed adapter or claim of account availability.

Bind the verification to a server-created signup transaction or signed-in account, expected phone, session nonce, purpose, service and expiry. Consume approved proof once and rotate/create only the appropriate scoped session. Do not accept an arbitrary browser-supplied verification SID, a composer-open event or an unverified webhook. Existing-account recovery, phone reassignment, messaging consent, Natural activation and debit approval keep their independent checks.

Validate iPhone and independently establish Android/SMS support before making this the sole onboarding route. Account-assigned verification lines may fall back to a shared pool, so the verification thread may differ from the continuing agent thread. Supersedes ADR-001's three-role deployment and ADR-004's immediate Graphile installation.

## ADR-033 — Audited rechecking of the same accepted connection

**Date:** September 26, 2026. **Owner:** Natural connection implementation. **Affected:** production hosted account activation, canonical ownership checks, failed-acceptance recovery and setup feedback. **Status:** implemented locally; focused tests and actual provider reads passed. Persisted recovery and connected UI are pending the accepted tester's explicit recheck. Extends ADR-031; founder local-test/release approval remains required.

**Context:** the first distinct tester's accepted-invitation callback was delivered and quarantined. The validator incorrectly required the platform-owned canonical event's party relationship to match the accepted payload's customer/delegator. Those identities are distinct. Webhook source may be either bound party; the observed callback's source was the platform. Meanwhile, **Check setup** only reread local state, leaving a blocked record unchanged without meaningful feedback. The separate platform-owner `SELF_INVITATION` rejection requires a different consenting customer; it does not justify bypassing customer enrollment.

**Decision:** validate canonical event ownership against the configured platform, then independently bind the exact invitation, agent, customer/delegator and platform/delegatee before checking current delegation and the agent-default wallet. Add an authenticated, same-origin POST refresh with an empty body that derives the saved event from the current account and repeats only these canonical reads. Require existing account assurance; retain fresh passkey assurance for initial invitation creation. Never accept client-provided provider identities, turn return navigation into acceptance, recreate an invitation or enable money movement through refresh.

**Recovery and audit:** apply a 15-second per-connection cooldown and the existing 90-second generation/token-fenced lease. Migration021 records each admitted recheck's prior connection state and quarantine reason, timing and result. Reject payload conflicts or unrelated quarantines before provider I/O and again before committing activation. A successful recheck can resolve only the matching acceptance-validation quarantine; preserve its old reason in the journal. Workers leave blocked records blocked until an authenticated recheck. The UI provides explicit checking/result feedback while background GET polling remains a local-state read.

**Alternatives and cost:** automatically reprocessing every quarantine risks dismissing payload conflicts or repeating a persistent contract error. A direct status override or replacement invitation would discard evidence and bypass canonical checks. An operator-only reset adds support work for recoverable validation failures. Account-bound rechecking preserves identity and history, at the cost of one new route, a small audit table and bounded provider-read latency. The cooldown is not evidence that an unchanged connection has been freshly revalidated, so UI feedback must avoid that claim.

**Evidence:** 113 focused tests across five files passed; the full check then passed formatting, all-workspace TypeScript, 786 tests across 44 files and the optimized Next.js build. Actual GET-only checks of the retained acceptance, customer, current grant and selected agent-default wallet now pass, including the effective 1,000-cent transaction limit and USD currency. Public readiness is 200 with money movement disabled, anonymous POST refresh is 401, and the founder's separate pending account visibly transitions from checking to explicit waiting feedback. The existing accepted tester record is still blocked pending the fixed action; no connected UI, bank funding/cash-out, production debit or settlement is established by these checks. No financial mutation, push or deployment occurred.

**Rollout and revisit:** additive migration021 is applied to both local databases and the local runtime restarted at the same temporary passkey origin. The next step is for the accepted tester to reload and select **Check setup**. Revisit recovery if Natural changes event ownership semantics, an accepted callback never arrives, or a forwarded invitation/phone-binding test fails. Missing evidence, expired invitations and payload conflicts need explicit supported procedures; this change grants no general quarantine override.
